Flingra · Delivery map · Backend

What to build next

A phased implementation path for the Go API, with deliverables the frontend can integrate against.

Product direction: One app; male/female categories only; minimum age 21. Backend owns eligibility, connection rules, discovery privacy, payment state, and safety escalation. Legal/provider approval is a go/no-go for payment holds, biometric checks, mandatory GPS, and emergency calling.

Current state: scaffold only Proposed endpoints and payloads are documented in backend/README.md; implement and freeze them in OpenAPI before integration.

Build sequence

0 · Contract and project foundation

  • Get written legal/privacy/payment-provider go/no-go for ID and gender checks, GPS, archived accounts, live/calls, meetup money flow, and check-in escalation.
  • Create Go module/toolchain, `cmd/api`, focused `internal` packages, config validation, Docker/local MySQL, migrations, CI formatting/tests.
  • Define `/api/v1`, common error envelope, request IDs, OpenAPI conventions, cookie/CSRF/CORS policy.

Deliverable: runnable health endpoints, reviewed OpenAPI starter, reproducible local environment.

Frontend handoff: API base URL, CORS/origin requirements, error schema, cookie/CSRF integration notes.

1 · Account, session, and eligibility foundation

  • Email/password + verified email and Google OIDC; require DOB 21+, government-proof upload/admin review, male/female gender check, and emergency-contact phone.
  • Argon2id password hashing; opaque server-side session cookie; CSRF and exact-origin checks; rate limits and generic auth responses.
  • Server-owned account states for verification pending/rejected, profile incomplete, active, suspended, and archived.

Deliverable: stable auth endpoints and contract-tested session/account-state responses.

Frontend handoff: signup/login payloads, cookie behavior, CSRF token/header, recovery and error states.

2 · Profile, preferences, and discovery

  • Member/profile schema and migration; private owner DTO separate from public profile DTO.
  • Profile fields/media minimums and moderation queue; 3-10 photos, 2-10 videos, max 30 seconds; proposed caps 10/100 MB.
  • GPS updates and separate manual search area; return only approximate location; implement server-side preference-compatible discovery.

Deliverable: `/me`, profile, preference, public-profile, and discovery operations with MySQL integration tests.

Frontend handoff: exact DTOs/enums, field validation limits, cursor rules, empty result and profile-unavailable behavior.

3 · Connections, messaging, live, and calls

  • Male-to-female connection requests, approve/decline and hard cap after 3 rejections from the same recipient.
  • Conversation opened on approval, requester sends first message; both can message afterward.
  • Female-only live stream, accepted audio/video calls, call-credit ledger, in-app/push notification fan-out.

Deliverable: tested authorization, participant rules, tokens, server-side call metering, provider adapters.

Frontend handoff: request states, message rules, live/call lifecycle, prices, notification preferences.

4 · Booking, payment, and safety operations

  • Booking date, time, duration, and exact location; share destination only after both accept.
  • Provider-held meetup funds, requester confirmation, manual staff release, disputes/refunds; no automatic payout.
  • One-minute check-ins during accepted booking; after 3 missed prompts call emergency contact; allow immediate SOS.
  • Admin review queues for age proof/media/reports/safety/payment/restoration; MFA, least privilege and audit events.

Gate: no fund flow or emergency automation without approved providers, legal review, trained staff, and tested escalation/fallback.

5 · Block/report and soft deactivation

  • Block/unblock/list with immediate bidirectional discovery exclusion.
  • Report reasons and report submission with restricted staff access, redacted logs, idempotency/duplicate handling.
  • Soft-deactivate and archive account, hide everywhere, revoke sessions; restoration by staff application only.
  • Block/report endpoints, safety review and event audit; define account archive retention with counsel.

Deliverable: safety endpoints, privacy/deletion behavior, authorization and abuse tests.

Frontend handoff: report categories, neutral receipts, block effects, deletion status/grace period.

6 · Reliability, security, and launch readiness

  • Timeouts, graceful shutdown, structured redacted logs, health/readiness, Sentry/equivalent, backup and restore runbook.
  • OpenAPI validation/contract tests; migration upgrade tests; MySQL integration and concurrency/idempotency tests.
  • Review CORS/cookies/CSRF, rate limits, least privilege, secret handling, data retention, and abuse cases.
  • Staging contract walkthrough with frontend; resolve all mismatched DTOs/errors before launch.

Done when: core APIs pass security and integration cases and the frontend can complete key journeys against staging.

Definition of ready for each endpoint

  1. OpenAPI operation includes request/response, auth, field visibility, limits, and error codes.
  2. Authorization and abuse/rate-limit behavior are decided and tested.
  3. Responses omit private data by construction; handlers do not serialize database models.
  4. Tests cover success, validation, forbidden access, and failure states.
  5. Frontend receives example payloads and an integration note; contract changes are communicated before merge.

Defer or gate

VIP/VVIP memberships and fixed host rewards are deferred. Real money movement, face-based gender rejection, mandatory GPS, indefinite archive retention, calls/live, and automated emergency contact need documented legal/privacy/provider approval and operational readiness before launch.
